# Sahakar Sahayak — Project Overview

**Sahakar Sahayak** ("cooperative helper") is a multilingual (English, Hindi, Marathi, Tamil) AI legal assistant for **Indian cooperative-society law**. It answers questions from the actual text of six Cooperative Societies Acts, cites the exact sections it relies on, and verifies its own citations before showing an answer — built to make a dense, fragmented body of statute law usable by ordinary people who run India's cooperative societies, not just lawyers.

This document explains what the project contains, the technology behind it, and — with real, sourced numbers — how it can help common people across India at scale.

---

## 1. The problem it addresses

Cooperative societies (credit societies, housing societies, dairy/agricultural cooperatives, etc.) are governed by a **patchwork of central and state Acts**, each with hundreds of sections, amendments, and state-specific rules. In practice:

- Society members and elected office-bearers (chairpersons, secretaries, committee members) are rarely lawyers, and are frequently more comfortable in a regional language than in legal English.
- Getting a straight, citable answer to "how do we conduct society elections" or "what's the quorum for a general body meeting" today usually means hiring a lawyer, visiting a Registrar's office, or wading through a scanned Gazette PDF.
- This friction disproportionately affects rural and semi-urban members — exactly the population that cooperative societies were designed to serve.

Sahakar Sahayak is built to close that gap: a free-to-run, citation-grounded, multilingual assistant that anyone can query in their own language.

## 5. The AI pipeline — how an answer is produced

Every question passes through four explicit stages (`apps/backend/src/routes/chat.ts`):

1. **Triage** — a single grammar-constrained JSON call extracts the question's language, intent, whether it should be escalated to a human, and English search terms (so a Hindi or Tamil question can still retrieve English-language statute text).
2. **Retrieve** — two retrieval methods are combined with **reciprocal-rank fusion**:
   - **BM25** keyword search (`lib/rag/search.ts`)
   - **bge-m3** embedding cosine similarity (`lib/rag/embeddings.ts`)
   The user's own state jurisdiction is ranked above the central corpus. If no embedding server is available, the system gracefully falls back to BM25 alone.
3. **Answer** — the LLM streams its answer using *only* the retrieved sections as sources, citing them inline as `[n]`.
4. **Verify** — every citation is checked against its source text. Sources the model didn't actually cite are dropped; unsupported or invented citations lower the answer's confidence score. Low-confidence or uncited answers are automatically routed to an **admin review queue** rather than shown as authoritative.

This "retrieve → answer → verify" loop — rather than an ungrounded chatbot reply — is the core design decision that makes the tool usable in a legal-accuracy-sensitive domain.

### Models used

| Purpose | Local / development | Hosted / production (free-tier friendly) |
|---|---|---|
| Chat / reasoning | **Qwen3.5-4B-GGUF (Q4_K_M)** via llama.cpp, port 8080 | **Groq** — `openai/gpt-oss-120b` (OpenAI-compatible API) |
| Embeddings | **bge-m3-GGUF (Q8_0)** via llama.cpp, port 8081 | **Cloudflare Workers AI** — `@cf/baai/bge-m3` (10,000 free neurons/day) |

Because both hosted options are free-tier and OpenAI-API-compatible, the entire backend can be deployed and run **at zero recurring model cost**.

## 7. Multilingual support

The UI, content, and answers are fully localized in **English, Hindi (हिन्दी), Marathi (मराठी), and Tamil (தமிழ்)**, including per-language speech/TTS locale codes (`en-IN`, `hi-IN`, `mr-IN`, `ta-IN`). This directly targets the literacy/language barrier that keeps most legal-tech tools out of reach for non-English-fluent users — which, per the readership data above, is the majority of cooperative-society members in India.

## 8. Features

- **Conversational legal assistant** with streamed, citation-backed answers (Server-Sent Events).
- **Step-by-step checklists ("Procedures")** for common actions — e.g. registering a society or holding elections — served from `corpus/procedures/*.json`.
- **Conversation history** — signed-in users can revisit past questions and answers.
- **Feedback loop** — thumbs up/down on every answer, feeding an admin review queue.
- **Confidence-based human review queue** — any answer the verification step can't fully support is queued for a human/admin to check.
- **Admin console** — document upload & reindexing, glossary management, review queue triage.
- **Role-based accounts** — member vs. admin, with a demo admin account for evaluation (`test@gmail.com` / `1234`).
- **Mock mode** (`NEXT_PUBLIC_CHAT_MODE=mock`) — lets the frontend be developed/tested without needing a running model.

## 9. Real metrics — evaluation results

The project ships its own evaluation harness: **152 questions** (9 topics × jurisdictions × 4 languages), each with an expected set of statute sections taken directly from the ingested Acts. Running it scores retrieval accuracy, citation correctness, response language, and the verification step.

**Latest recorded run** (local model, Qwen3.5-4B Q4_K_M, on a single RTX 3060 Laptop GPU with 6 GB VRAM — i.e., consumer-grade hardware, not a data-center GPU):

| Language | Retrieval accuracy | Cited correctly | Correct script | Avg. response time |
|---|---|---|---|---|
| English | 100% | 97% | 100% | ~13 s |
| Hindi | 95% | 89% | 100% | ~19 s |
| Marathi | 89% | 87% | 100% | ~22 s |
| Tamil | 93% | 97% | 100% | ~23 s |

Notes for honesty and context:
- "Cited correctly" means at least one of the expected sections appears among the sources the answer actually cites.
- The verification pass separately flags **15–25% of citations** as not fully supporting their sentence; these are shown as *unverified* in the UI and routed to the review queue rather than presented as settled fact.
- These numbers come from a small, curated eval set on modest local hardware — they demonstrate the pipeline works and is measurable, not that it is infallible. Response times would be materially faster on the hosted Groq backend.

## 10. Deployment model — why this is affordable to run at scale

| Model | Stack | Cost |
|---|---|---|
| **Free-tier hosted** | Render (free web service, backend only) + Supabase (free Postgres) + Groq (free chat API) + Cloudflare Workers AI (free embeddings, 10k neurons/day) + Vercel (frontend) | **$0/month**, no GPU required |
| **Fully self-hosted** | `docker compose up` — Postgres, llama.cpp chat model (CUDA), llama.cpp embedding model, backend, frontend, all in containers | Only the cost of a GPU-capable machine; **no per-query API cost, works offline from the internet after model download** |

Because the entire stack can run for free on hosted infrastructure, or entirely offline on a single consumer GPU, **state cooperative departments, NGOs, panchayats, or civic-tech volunteers can deploy an instance with no recurring budget** — a meaningfully lower barrier than commissioning custom legal software.

## 11. How this can help common people of India at scale

Putting the pieces above together:

1. **Removes the cost barrier.** Routine cooperative-governance questions (registration steps, election procedures, audit requirements, dispute processes) currently often require paid legal consultation. A free, always-available, citation-backed assistant absorbs a large share of that routine demand — relevant to a base of **~6.2 lakh functional societies and ~29 crore members** (Ministry of Cooperation, Dec 2024) who need this kind of guidance regularly.
2. **Removes the language barrier.** With English, Hindi, Marathi, and Tamil support (and speech locales for read-aloud), members who are not comfortable in legal English — the majority in rural/semi-urban cooperatives — can ask questions in their own language and get answers in their own script.
3. **Builds trust the way legal information must.** The retrieve → answer → **verify** design means the system doesn't just generate plausible-sounding legal text — it cites exact sections and actively flags weakly-supported answers for human review, instead of silently hallucinating a citation. This is the difference between a "chatbot" and a defensible reference tool.
4. **Is measurably improvable, not a black box.** The 152-question, 4-language evaluation harness gives a repeatable way to track whether quality is improving as the corpus grows or models change — important for anyone (a government body, an NGO) considering deploying it as public infrastructure.
5. **Scales geographically for near-zero marginal cost.** The corpus currently covers 6 jurisdictions (central + 5 states); the ingestion pipeline (`scripts/ingest.mjs`) is designed to onboard additional state Acts without code changes. Given free-tier hosting, expanding this to more of India's states/UTs is a data problem, not an infrastructure or budget problem.
6. **Complements, not replaces, the Registrar/legal system.** It is explicitly designed to answer "what does the law say and where," and to hand off low-confidence or contentious matters to a human review queue — positioning it as a triage and self-service layer in front of the existing legal/administrative system, not a replacement for it.

**Honest framing:** today this is a **working, evaluable prototype covering one legal domain (cooperative societies) across 6 of India's jurisdictions** — not a finished nationwide legal-aid platform. Its value at "large scale" is best understood as a **proven, low-cost, replicable template**: the same triage → retrieve → answer → verify architecture, corpus-ingestion pipeline, and multilingual UI could be extended to more states, more cooperative-adjacent regulations, or in principle other domains of Indian law that share the same "many Acts, low public access" problem — provided each expansion goes through the same evaluation discipline this project already has in place.

## 12. Current limitations (stated plainly)

- **Single legal domain**: covers cooperative-society law only — not IPC/CrPC, tenancy, labor, family law, etc.
- **Partial geographic coverage**: 6 of India's 28 states / 8 union territories currently have ingested Acts.
- **Uneven language performance**: per the eval table, Marathi and Hindi trail English on citation accuracy (87–89% vs. 97%), though script accuracy is 100% across all four.
- **Verification reduces but does not eliminate errors**: 15–25% of citations are still flagged unverified and require human review.
- **Not a substitute for a lawyer** in adversarial disputes, litigation, or anything beyond informational/procedural guidance.
- **No production usage analytics yet** — the population figures in this document describe the addressable market, not actual current users of this specific deployment.

## 13. Running it locally (from README.md)

```bash
npm install
cp apps/backend/.env.example apps/backend/.env   # paste your Supabase DATABASE_URL
npm run dev            # starts chat model, embedding server, API, and UI together
```

`npm run dev` runs four processes concurrently: the chat model server on port 8080 (llama.cpp, downloads Qwen3.5-4B on first run), the embedding server on port 8081 (bge-m3), the API on `http://127.0.0.1:4000`, and the UI on `http://localhost:3000`. Sign in with the demo admin (`test@gmail.com` / `1234`) or register as a member.
